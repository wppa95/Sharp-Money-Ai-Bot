Implement Full-Pool Rescan Rotation for Sharp Money Bot

We need a continuous full-pool rescan system that guarantees every active prop eventually gets rescanned. The current active Underdog pool is ~2.2M+ props.

### Core Requirements

- Every active prop must eventually be rescanned — including stable/unchanged props, previously rejected props, previously scored props, near-misses, watchlist props, and props whose lines have not moved.
- A previous rejection must NEVER permanently exclude a prop from future evaluation.
- Process the pool in bounded batches only. Do NOT try to process all 2.2M props at once.
- When 100% of the current active pool has been covered, automatically start the next rotation.
- Persist enough rotation state so the bot can safely resume after a restart (do not reset to zero on every restart).
- Continue indefinitely while the bot is running.

### Priority Order (scheduling only)

1. Tier 1 sports + All other sports (equal priority)
2. NFL / MLB (lowest priority)

Tier 1 sports and all other sports share the same priority level. NFL and MLB must still eventually be rescanned — they just get lowest priority. Do not remove any sports from monitoring. This is only a scheduling priority.

### Keep Task #121 completely intact

Do NOT remove or break the existing Task #121 stable-refresh system.

Keep:
- 120-second stable refresh
- stable batch processing
- watchlist refresh
- persisted alert deduplication
- removal handling
- alert_sent persistence
- bulk deduplication
- existing Telegram gates

There must now be two separate systems:

1. Stable Refresh (existing) – small recurring refresh for watchlist / recent props
2. Full-Pool Rotation (new) – covers the entire ~2.2M+ active pool in batches, including rejected and unchanged props

Do not combine their metrics.

### Progress Display Rules

Show human-readable progress only. NEVER display internal cursor values or database IDs.

Good example:
Rotation: #1
Progress: 18.4%
Coverage: 412,000 / 2,240,000 active props
Priority: Tier 1 + Other sports

When a rotation finishes:
Rotation #1: 100% complete
then automatically begin
Rotation #2: 0% complete

Progress must reflect actual full-pool coverage, not the stable-refresh batch.

API totals must **NOT** be shown in the display.

### Important Constraints

- Full-pool rescan **SHOULD** inflate the “Fetched from Underdog” and API totals for each prop that is rescanned.
- Keep these metrics tracked: API/fetch totals, active pool size, full-pool rescan coverage, stable refresh, candidate funnel, Telegram alerts.
- Removed / inactive props must NEVER be resurrected. Only currently active props may enter the rotation (use the same removal-safe logic already used in Task #121).
- A rescanned prop must still pass the normal scoring, direction, confidence, Bet Quality, tier, validation, live/pre-game, and Telegram deduplication gates. Do not auto-alert just because it was rescanned.
- No artificial Underdog API-call limit or budget. Batching exists only to control CPU / memory / DB load.
- Batch size must stay bounded.

### Rescan Fairness

Higher priority must not starve lower-priority sports. Every active prop must eventually get rescanned.
